# DSH：Codex 与 Codely 无缝切换工作流（V0--V2 实施方案）

> **用途**：本文档用于指导 Codex 在现有 DSH
> 仓库中落地一套可立即使用、可逐步自动化、最终可由 DSH 原生接管的
> Codex/Codely 协作工作流。\
> **推荐实施顺序**：先完成 V0 并验证；再按实际使用反馈实施 V1；V2 作为
> DSH 原生能力的设计与分阶段实现路线。\
> **核心约束**：先检查当前仓库和既有架构，再适配实施。不得假定目录、命令、Agent
> 接口或架构文件一定存在；不得覆盖已确认的 ADR 或用户未提交的工作。

------------------------------------------------------------------------

## 0. 给 Codex 的执行摘要

请先阅读本文档，再检查当前仓库中的
`AGENTS.md`、`CODELY.md`（如果存在）、现有开发规范、架构决策、Git 状态和
DSH 当前计划。

本次实施的目标不是立即开发一个临时 Agent
调度器，而是先建立一套低成本、可靠、可审计的交接协议：

1.  **V0：共享事实**------用仓库文件保存工作流规则、任务计划、长期记忆和交接
    Checkpoint；由用户手动切换 Agent。
2.  **V1：降低操作成本**------提供跨平台校验/初始化工具与 Agent 专用
    Skill/指令，让交接和恢复流程可重复执行。
3.  **V2：DSH 原生接管**------把任务、会话、Checkpoint、Agent
    适配器、工作区和写入权纳入 DSH 的统一管理。

**本轮默认先完成 V0**，并把 V1/V2
的实现边界、任务拆分和验收条件写入项目文档或
TODO。除非用户明确要求一次性实现全部阶段，否则不要在 V0
尚未验收时提前开发 V1/V2 的复杂自动化，更不要新建一个与 DSH
主架构平行的调度系统。

------------------------------------------------------------------------

## 1. 背景与目标

DSH 尚未完成期间，Codex 和 Codely
需要能够接力开发同一个工程。理想切换应满足：

-   不必把旧 Agent 的整段聊天历史复制给新 Agent。
-   新 Agent
    能迅速了解任务目标、已确认决策、当前代码状态、测试结果和下一步。
-   不重复实现已完成内容，不因上下文丢失而违反架构决策。
-   同一任务在同一工作区内始终只有一个写入者；并行任务通过独立分支/工作区隔离。
-   同一台电脑切换与跨电脑切换都可用。
-   交接记录能通过 Git 追溯，遇到异常退出可从仓库和代码重建状态。
-   现有文件和工作习惯能渐进迁移，不强制一次性重构。
-   将来由 DSH 统一管理 Task、Session、Checkpoint 和 Agent
    路由时，不必推翻 V0/V1 的概念模型。

### 1.1 非目标

V0/V1 不做以下事情：

-   不同步 Codex 与 Codely 的原生聊天历史、推理缓存或内部工具调用状态。
-   不假设两个产品支持互相恢复对方的会话。
-   不实现模型路由、模型 API 代理或新的 Agent Loop。
-   不自动覆盖用户文件、不自动执行破坏性 Git 命令、不自动强制推送。
-   不把 DSH 与 Unity、MGSD
    或某一个业务工程绑定；该工作流是通用工程协作能力。
-   不用一个无限增长的 Memory 文件代替任务计划和 Checkpoint。

------------------------------------------------------------------------

## 2. 设计原则

### 2.1 共享事实，而非共享聊天

共享内容分为四类：

1.  **稳定规则**：项目约束、工作流规则、已确认架构决策。
2.  **任务计划**：本任务目标、范围、验收标准、执行步骤。
3.  **当前状态**：已完成项、未完成项、风险、测试证据和下一步。
4.  **代码事实**：Git 分支、Commit、Diff、工作区状态和 CI 结果。

聊天历史只能作为补充参考，不是任务状态的权威来源。

### 2.2 单一事实来源

-   Git 是代码和版本历史的事实来源。
-   当前 Task 的 `task.md` 是目标、范围和验收标准的事实来源。
-   当前 Task 的 `plan.md` 是执行计划的事实来源。
-   当前 Task 的 `handoff.md` 是最近一次交接快照的事实来源。
-   ADR 是已确认架构决策的事实来源。
-   DSH 原生能力完成后，DSH 的 Task/Checkpoint Store
    成为运行状态的权威来源；Git 仍然是代码版本的权威来源。

同一信息不要在多个文件中重复维护；如有重复，明确哪一处是权威来源。

### 2.3 先读再写，先验证再交接

Agent 在开始任务前必须先检查项目约定、Task 状态、Git 状态和最近
Checkpoint。交接前必须检查 Diff、测试证据和敏感信息。不能只根据
`handoff.md` 的文字就假设代码与描述一致。

### 2.4 一个任务、一个写入者

-   同一个 Task 在同一个工作区中只能有一个 Agent 写入。
-   接手 Agent 必须确认上一个 Agent 已停止修改。
-   同一仓库的不同 Task
    可以并行，但应使用独立分支；有较大冲突风险时使用独立 Git Worktree。
-   不允许两个 Agent 同时修改同一工作区后再尝试合并"谁的上下文更新"。

### 2.5 交接应可恢复、可审计、可重复

交接不是一句"你接着做"，而是一个包含代码版本、任务状态、验证证据和写入权变化的显式协议。

## 3. 开始实施前的仓库侦察

Codex 必须先完成以下检查，并在执行摘要中简要报告结果：

1.  查看仓库根目录和 `docs/`、`.ai/`、`scripts/`、`.github/`
    等相关目录。
2.  检查 `AGENTS.md`、`CODELY.md`、README、贡献指南、开发规范、现有
    Task/Plan/Checkpoint/Memory/ADR。
3.  检查当前分支、HEAD、`git status --short`、未提交
    Diff、未跟踪文件和远程配置。
4.  搜索现有的任务 ID 规则、命名规则、脚本语言和测试框架。
5.  检查 DSH 已确认的架构决策；不要重新定义或覆盖现有 ADR。
6.  识别当前工作区是否已有用户正在进行的修改。

### 3.1 侦察后的适配规则

-   如果仓库已有等价目录或文件，优先扩展现有结构，不要再建一套平行体系。
-   如果 `AGENTS.md` 或 `CODELY.md`
    已有内容，只添加必要引用，不得整文件覆盖。
-   如果现有项目把 Agent
    说明放在其他位置，沿用既有约定并在新文档中注明映射。
-   不得删除、重置或覆盖未提交修改。
-   不得为了"让工作区干净"而运行 `git reset --hard`、`git clean -fd`
    或类似破坏性命令。
-   不得把与本任务无关的已有修改纳入交接提交。
-   若无法判断某项现有改动是否属于本任务，停止提交并报告，等待用户决定。
-   不得假定 `codely` 的 CLI 命令、会话恢复参数或 Skill
    目录；需要使用时先检查当前安装版本和官方/项目文档。

## 4. 目标目录结构

以下为推荐结构，**不是要求机械照搬**。先映射现有结构；只有不存在等价实现时才新建。

``` text
<repo-root>/
├── AGENTS.md                         # Codex 项目入口；若已有则增量修改
├── CODELY.md                         # Codely 项目入口；若该工具使用此文件
├── .ai/
│   ├── WORKFLOW.md                   # 两个 Agent 共用的工作流规则
│   ├── ARCHITECTURE.md               # 当前架构概要与重要约束
│   ├── MEMORY.md                     # 精简、稳定、可复用的工程知识索引
│   ├── adr/
│   │   └── ADR-xxxx-*.md              # 架构决策记录；沿用现有编号规则
│   └── tasks/
│       └── DSH-xxx/
│           ├── task.md                # 任务目标、范围、验收条件
│           ├── plan.md                # 分阶段计划与完成状态
│           ├── handoff.md             # 最新交接快照
│           └── log.md                 # 关键执行、测试和决策记录
└── docs/
    └── workflows/
        └── codex-codely-handoff-v0-v2.md
```

### 4.1 各文件职责

  --------------------------------------------------------------------------------------------------
  文件                    只负责什么                                    不应放什么
  ----------------------- --------------------------------------------- ----------------------------
  `WORKFLOW.md`           通用协作规则、交接和恢复步骤                  每日流水账、单个 Task 的细节

  `ARCHITECTURE.md`       架构概览、模块边界、重要约束与 ADR 索引       取代 ADR 的长篇决策讨论

  `MEMORY.md`             稳定且反复有用的事实、常见陷阱、资料索引      完整聊天记录、所有工具输出

  `task.md`               任务目标、范围、验收标准、依赖                逐步执行日志

  `plan.md`               工作分解、阶段、状态、依赖                    代码实现的详细复述

  `handoff.md`            当前交接点、已完成/未完成、测试证据、下一步   长期架构知识

  `log.md`                关键变更、实验、测试、异常及结论              每个无意义的命令输出
  --------------------------------------------------------------------------------------------------

### 4.2 Agent 入口文件要求

`AGENTS.md` 和 `CODELY.md`
应当保持短小。若适用，增加对共享规则的引用，例如：

``` md
## Shared Agent Workflow

Before modifying code, read `.ai/WORKFLOW.md` and the current task files:
- `.ai/tasks/<task-id>/task.md`
- `.ai/tasks/<task-id>/plan.md`
- `.ai/tasks/<task-id>/handoff.md`

Respect confirmed ADRs. Inspect Git status before editing.
Before handing off, update the task checkpoint and report code/test evidence.
```

注意： - 入口文件应符合对应 Agent 的真实加载规则。 - 如果 Codely
不自动读取 `CODELY.md`，应在 Codely 可用的项目指令/Skill
配置中建立等效入口，不得仅因为文件存在就假定它生效。 -
共享规则不能依赖只有一个 Agent 才理解的专有语法。

## 5. Task 文件模板

### 5.1 `task.md`

``` md
---
schema_version: 1
task_id: DSH-023
title: "实现 Task Scheduler 的恢复能力"
status: PLANNED
priority: P1
created_at: "YYYY-MM-DDTHH:mm:ss+08:00"
updated_at: "YYYY-MM-DDTHH:mm:ss+08:00"
---

# 目标

一句话描述要交付的能力和用户价值。

## 背景

解释为什么需要此任务，以及相关上下文。

## 范围

### In scope
- 本次明确要实现的内容。

### Out of scope
- 本次明确不做的内容。

## 验收标准

- [ ] 功能行为满足约定。
- [ ] 自动化测试通过，或记录不能自动验证的原因。
- [ ] 相关文档更新。
- [ ] 不违反已确认 ADR。
- [ ] 无未解释的新增回归。

## 依赖与约束

- 依赖的任务、模块或外部条件。
- 适用的 ADR。
- 兼容性和安全要求。

## 用户决策

- 需要用户确认的问题；没有则写“无”。
```

模板里的 Task
ID、时间、状态和示例任务仅为示意。实际值必须遵循仓库现有命名约定，不得将示例当作真实任务。

### 5.2 `plan.md`

``` md
# Execution Plan

## Phase 1 — <阶段名称>

- [ ] <具体、可验证的工作项>
- [ ] <具体、可验证的工作项>

状态：NOT_STARTED | IN_PROGRESS | DONE | BLOCKED

## Phase 2 — <阶段名称>

- [ ] <具体、可验证的工作项>

状态：NOT_STARTED | IN_PROGRESS | DONE | BLOCKED

## 验证计划

- 命令：
- 预期结果：
- 实际结果：
- 未执行项及原因：
```

计划项应尽可能小且可验证。完成状态必须依据代码或验证证据，而不是仅依据
Agent 的主观判断。

### 5.3 `handoff.md`

这是跨 Agent 接力的核心文件。建议采用下面的结构，并保持简短：

``` md
---
schema_version: 1
task_id: DSH-023
state: HANDOFF_READY
previous_agent: codex
next_agent: codely
branch: "task/DSH-023"
base_commit: "<接手任务时的基线 commit>"
tested_code_commit: "<最近一次测试所针对的代码 commit>"
updated_at: "YYYY-MM-DDTHH:mm:ss+08:00"
---

# Handoff Checkpoint

## 一句话状态
当前做到哪里，距离完成还差什么。

## 已完成
- 已实现的行为与对应文件/模块。
- 重要实现选择及其依据。

## 未完成
- 明确未完成的功能或验证。
- 不要把“尚未验证”描述成“已完成”。

## 当前代码与 Git 状态
- 分支：
- 最近 commit：
- 工作区是否干净：
- 是否已推送远程：
- 与任务无关的未提交改动：

## 验证证据
- 命令：
- 结果：PASS / FAIL / NOT_RUN
- 关键输出或报告位置：
- 测试对应的代码 commit：
- 未执行验证及原因：

## 已知问题与风险
- 问题、复现条件、影响范围和已尝试的办法。

## 重要约束
- 需要遵守的 ADR 或接口契约。
- 明确不能做的改动。

## 下一步
1. 优先级最高且可以直接开始的动作。
2. 下一动作。
3. 完成后应执行的验证。

## 需要用户决策
- 无，或逐条列出必须由用户决定的问题。
```

规则： - 不要在 `handoff.md` 内写入 API
Key、Token、密码、私有凭证或不必要的个人数据。 - `tested_code_commit`
应记录测试实际针对的代码版本。仅更新交接文档不应被误认为重新验证了产品代码。 -
如果 Git
状态不干净，必须列明未提交和未跟踪文件；不允许把"工作区干净"作为默认值。 -
如果没有运行测试，应明确写 `NOT_RUN` 和原因。 -
不要在同一个提交内写一个无法预先知道的自身 Commit Hash。接手方应从 Git
历史读取最新 HEAD。 - 若 Checkpoint 与真实代码、Git
状态或测试报告不一致，以可验证的实际状态为准，并标记冲突。

### 5.4 `log.md`

只记录对后续开发有价值的节点，例如：

``` md
# Task Log

## YYYY-MM-DD — <事件>
- 变更：
- 证据：
- 结论：
- 对后续工作的影响：
```

不要复制完整 Agent 对话或大量重复日志。若日志由脚本/CI
生成，应链接到可追溯的报告。

## 6. 统一 Task 状态机

建议状态：

-   `PLANNED`：任务已定义，尚未开始。
-   `IN_PROGRESS`：已有唯一写入者正在执行。
-   `HANDOFF_READY`：当前 Agent 已停止修改并完成交接快照，等待接手。
-   `REVIEW`：实现者已声明完成，等待独立审查/验收。
-   `BLOCKED`：被依赖、环境、决策或技术问题阻塞。
-   `DONE`：验收条件全部满足，结果已记录。
-   `CANCELLED`：用户明确取消；保留历史，不直接删除 Task 记录。

允许的主要转换：

``` text
PLANNED -> IN_PROGRESS
IN_PROGRESS -> HANDOFF_READY
HANDOFF_READY -> IN_PROGRESS
IN_PROGRESS -> REVIEW
REVIEW -> IN_PROGRESS       # Review 发现问题，退回修复
REVIEW -> DONE              # 验收通过
IN_PROGRESS -> BLOCKED
HANDOFF_READY -> BLOCKED
BLOCKED -> IN_PROGRESS      # 阻塞已解除
PLANNED -> CANCELLED
IN_PROGRESS -> CANCELLED    # 需先记录未完成改动和处理决定
```

约束： - `DONE` 不是"Agent 说做完了"，而是验收标准通过并有证据。 -
`HANDOFF_READY` 表示旧写入者已停止修改，不代表代码已通过最终验收。 -
`BLOCKED` 必须写清阻塞原因、已尝试方法以及需要谁做什么。 -
状态转换应有时间、执行者和理由记录。 - V0 用文档约定状态；V1
用脚本校验；V2 由 DSH 状态机强制执行。

## 7. V0：立即落地的手动交接流程

### 7.1 V0 目标

不用新服务、不依赖额外 API、不依赖跨产品会话恢复，只靠仓库文件和 Git
即可完成同一电脑与跨电脑接力。

### 7.2 V0 实施任务

1.  完成第 3 节的仓库侦察。
2.  找到现有 Agent 指令文件并增量添加共享工作流入口。
3.  创建或适配 `.ai/WORKFLOW.md`，明确：
    -   开始任务前如何读取上下文；
    -   如何核对 Git 状态；
    -   如何建立/更新 Task；
    -   如何交接；
    -   如何恢复；
    -   如何记录测试；
    -   如何处理架构决策冲突；
    -   哪些操作必须先获得用户许可。
4.  创建或适配 `.ai/ARCHITECTURE.md` 和
    `.ai/MEMORY.md`。只录入当前可确认的事实，不要猜测或从旧聊天中自动补齐未验证的架构。
5.  建立 Task 模板和 Checkpoint 模板。
6.  选择一个真实但范围可控的 DSH 任务进行试点。
7.  用 Codex -\> Codely 和 Codely -\> Codex 各完成一次真实交接。
8.  记录问题并修正工作流，避免只做文档而不验证可用性。

### 7.3 交接操作：旧 Agent 执行

1.  停止新增功能开发，进入交接模式。
2.  读取当前 `task.md` 和 `plan.md`，确认任务范围没有悄然改变。
3.  检查：
    -   当前分支和 HEAD；
    -   `git status --short`；
    -   已跟踪文件 Diff；
    -   未跟踪文件；
    -   是否混入与当前 Task 无关的修改。
4.  更新 `plan.md` 的真实进度。
5.  更新
    `handoff.md`：完成项、未完成项、风险、测试命令/结果、测试对应代码
    Commit、下一步。
6.  如果适合，运行任务相关测试。不要为了交接而宣称未执行的测试通过。
7.  检查交接文件是否含凭证、私密信息或无关大段日志。
8.  只对本 Task 相关文件进行明确的 WIP/Checkpoint
    Commit；不要将无关改动一并提交。
9.  对跨设备交接，若有授权且远程已配置，Push
    任务分支；否则明确报告尚未同步，不能声称对方设备已能接手。
10. 最后把状态改为 `HANDOFF_READY`，明确旧 Agent
    已停止写入，并输出简洁交接摘要。

**Git 安全规则：** - 不运行强制 Push。 - 不运行
`reset --hard`、`clean -fd` 等破坏性命令。 -
不自动解决与任务无关的冲突。 -
如果提交会包含不明归属的文件，先停止并报告。 -
如果仓库规定提交必须由用户执行，则只准备好文件和建议命令，不自行提交。 -
不得把敏感配置、密钥或构建产物提交进仓库。

### 7.4 接手操作：新 Agent 执行

1.  读取 Agent 入口文件和 `.ai/WORKFLOW.md`。
2.  读取对应 Task 的 `task.md`、`plan.md`、`handoff.md`，只按需读取相关
    ADR 和 Memory。
3.  检查当前工作区、分支和 HEAD；跨设备时先
    Fetch，再按仓库规范切换到正确分支。
4.  确认旧 Agent 已停止修改，且当前任务没有另一个写入者。
5.  将 `handoff.md` 与真实代码和 Git 历史核对：
    -   文件是否存在；
    -   Checkpoint 所述 Commit 是否可达；
    -   已完成项是否能从代码中确认；
    -   测试是否确实执行；
    -   测试针对的 Commit 是否匹配；
    -   是否存在未提交 Diff 或冲突。
6.  如有不一致，先修正状态认知，并记录差异；不得盲目执行"下一步"。
7.  将 Task 状态改为 `IN_PROGRESS`，记录接手 Agent 与时间。
8.  从 `plan.md` 中第一个未完成且未被阻塞的事项继续。
9.  不重复实现已经完成且验证通过的内容。
10. 开始编码前若发现架构决策冲突、工作区归属不明或关键上下文缺失，应先暂停并向用户报告。

### 7.5 推荐交接提示词

交接提示词应由 `.ai/WORKFLOW.md` 作为权威版本维护，避免每个 Agent
使用不同版本。可以从下面的文本开始：

**Handoff：**

> 按项目共享工作流交接当前 Task。停止新增开发；检查 Git
> 分支、HEAD、Diff、未跟踪文件和测试证据；更新 `plan.md`、`handoff.md`
> 与必要的
> `log.md`；明确完成项、未完成项、风险、下一步和需要用户决定的问题。只处理当前
> Task 相关变更。遵循仓库提交与推送政策，不要执行破坏性 Git
> 操作。最后报告实际保存/提交/推送状态，不得声称未完成的步骤已经完成。

**Resume：**

> 接手当前 Task。先读取 Agent
> 入口文件、共享工作流、`task.md`、`plan.md`、`handoff.md` 和相关
> ADR；检查真实 Git 状态，并核对 Checkpoint
> 与代码/测试证据。确认旧写入者已停止且当前任务没有其他写入者后，再把
> Task 转为
> `IN_PROGRESS`，从第一个未完成事项继续。不要重复已完成工作，不要擅自修改已确认
> ADR。若状态不一致或存在数据丢失风险，先停止并报告。

## 8. V0 的 Git 与多设备策略

### 8.1 同一台电脑切换

-   最稳妥方式：在同一 Task 分支上提交一个交接 Checkpoint，再启动另一
    Agent。
-   如果暂时不能提交，必须明确记录工作区 Diff，并确认新 Agent
    使用的是同一个工作区；这种情况不适合跨设备接力。
-   切换前关闭/停止旧 Agent 的写入操作，避免两个 Agent
    同时修改相同文件。

### 8.2 不同电脑切换

1.  旧电脑更新 Task 文档和 Checkpoint。
2.  在允许的情况下 Commit 并 Push 任务分支。
3.  新电脑 Fetch 远程分支。
4.  检查 HEAD 与 Checkpoint 是否一致，再接手。
5.  完成后仍在任务分支继续工作，按既有项目规则合并。

GitHub 上的文件可共享，不代表本地未提交修改自动同步。没有 Commit/Push
的变更不能视为已跨设备交付。

### 8.3 并行开发

-   每个并行 Task 独立分支。
-   文件重叠较多、构建输出或工具状态可能互相干扰时，使用独立 Worktree。
-   不同 Agent 不得共用同一工作区同时写入。
-   合并前由任务负责人核对接口契约、ADR、测试和冲突。
-   不要为了减少分支数量而让多个 Agent 同时修改同一任务。

## 9. V0 验收标准

V0 只有满足以下条件才算完成：

-   [ ] 两个 Agent 都能通过各自的项目入口找到共享工作流。
-   [ ] 新 Task 可以按统一模板创建。
-   [ ] Checkpoint 能明确记录完成项、剩余工作、测试证据和下一步。
-   [ ] Codex -\> Codely 接力成功，且没有重复实现已完成内容。
-   [ ] Codely -\> Codex 接力成功，且没有丢失关键上下文。
-   [ ] 同一电脑切换流程经过一次真实验证。
-   [ ] 跨电脑流程经过一次验证，或明确记录尚未具备的远程条件。
-   [ ] Agent 不会因读取过时 Checkpoint 就直接覆盖当前工作区。
-   [ ] 已确认 ADR 不会被 Agent 擅自覆盖。
-   [ ] 未提交的用户工作不会被重置、清理或意外纳入提交。
-   [ ] 文档没有凭证，且没有依赖未经确认的 CLI 命令。
-   [ ] 用户知道当前任务的真实状态、未完成项和风险。

## 10. V1：可重复的交接工具与 Agent Skills

### 10.1 目标

V0
验证通过后，减少手工操作与格式错误，但仍保持轻量、可解释，不引入完整的调度服务。

### 10.2 建议新增能力

先检查项目现有脚本语言和工具链。优先使用仓库已经采用的跨平台方案；若无约定，可使用
Python 标准库实现小型命令行工具，避免新增重量级依赖。

建议提供类似以下的操作（命令名称仅为接口示例，应按仓库实际规范定名）：

``` text
new-task <task-id> [--title "..."]
validate-task <task-id>
handoff-check <task-id>
resume-check <task-id>
checkpoint-report <task-id> [--json]
```

这些操作默认是只读或显式写入，不得静默执行提交、推送或覆盖代码。

#### `new-task`

-   从模板创建 Task 目录和四个标准文件。
-   校验 Task ID 不重复。
-   填入基础字段和初始状态。
-   不创建 Git 分支，除非仓库已明确规定此行为且用户授权。

#### `validate-task`

-   检查必需文件是否存在。
-   检查必需字段、合法状态、Task ID 一致性和更新时间格式。
-   检查完成项、测试证据和下一步是否缺失。
-   对无效内容给出行号/文件名和可操作的修复建议。
-   V1 初期不要求采用复杂 YAML
    库；先评估现有依赖和安全性，再决定解析方式。

#### `handoff-check`

-   输出 Git 分支、HEAD、工作区是否干净、Diff
    文件列表、未跟踪文件和远程同步状态。
-   对无关变更、Checkpoint 缺失、测试证据缺失给出警告。
-   不自动丢弃、暂存或提交文件。
-   如检测到敏感信息风险，只给出检查提示，不把敏感内容打印到终端日志。

#### `resume-check`

-   检查当前分支与 Task 声明是否一致。
-   检查当前 HEAD 与 Checkpoint 的关系。
-   检查 Task 状态是否允许接手、是否存在明显的过时状态。
-   检查是否有未提交修改或可能的并发写入风险。
-   输出 `READY`、`WARNING` 或 `BLOCKED`，并说明原因。

#### `checkpoint-report`

-   输出可供人或 Agent 快速读取的精简摘要。
-   可选 JSON 输出供未来 DSH 适配器使用。
-   JSON 输出应有 `schema_version`，并保持字段稳定。
-   不将完整日志、全部 Git Diff 或秘密信息塞入报告。

### 10.3 Skills / 自定义指令

在确认 Codex 与当前 Codely
版本的真实扩展机制后，为两边建立等价的工作流入口：

-   `handoff-task`：执行交接前检查、更新交接文件、输出保存/同步结果。
-   `resume-task`：读取 Task 和 Checkpoint、核对工作区、确认接手后继续。
-   `review-task`：对照验收标准和 ADR 做独立审查。

Skill 的核心逻辑应引用仓库内的 `.ai/WORKFLOW.md`，不要在两个 Agent 的
Skill 文本里复制两套不同规则。

如果某个 Agent 不支持相同的 Skill
机制，则使用它实际支持的指令文件或可执行脚本；不为了形式一致而依赖不存在的功能。

### 10.4 V1 的安全边界

-   默认只检查、不自动提交、不自动推送。
-   不运行破坏性 Git 命令。
-   不读取或输出 `.env`、凭证文件等秘密内容。
-   脚本应在 Windows、macOS 及项目支持的环境下测试。
-   解析 Markdown/YAML
    时，未知字段应尽量保留；校验工具不得因格式化而重写整份文件。
-   不允许脚本未经确认就把状态改成 `DONE`。
-   任何自动修复都应先展示将修改的文件和差异，或只处理确定无风险的模板初始化场景。

### 10.5 V1 验收标准

-   [ ] 可创建一个新的 Task 模板目录。
-   [ ] 缺字段、非法状态、Task ID 不一致会被检测出来。
-   [ ] 交接前能显示 Git 状态与风险，不会自动清理修改。
-   [ ] 恢复检查能识别错误分支、过时 Checkpoint 和未同步风险。
-   [ ] 同一套共享规则可由两个 Agent 调用。
-   [ ] 工具对未知字段和已有文件采取非破坏性处理。
-   [ ] Windows/macOS 的目标环境至少完成基础测试。
-   [ ] 脚本输出可被人直接阅读，且有可选的稳定 JSON 格式。
-   [ ] V0 的手动流程仍可在工具不可用时执行。

## 11. V2：由 DSH 原生接管

### 11.1 目标定位

V2 不应只是给 V1 脚本套一个 UI，而是将经过验证的交接协议变成 DSH
的原生能力。

遵循 DSH 的既定方向： - DSH 是唯一入口，拥有
Task、Session、Plan、Checkpoint 和共享 Memory 的权威状态。 - Agent
负责具体执行；Codex 与 Codely 是可替换的执行端。 - Agent
切换不依赖原生聊天历史可以跨产品迁移。 - 代码依旧由 Git 管理；DSH
保存可追溯的 Git 引用和验证证据。 - 必须遵循现有 DSH 架构和已确认
ADR；本文不是授权修改既定架构的理由。

### 11.2 建议的逻辑模块

以下是职责划分建议，不是要求按这些名字新建类或服务。先映射现有 DSH
组件，复用已有能力。

  逻辑职责               主要职责
  ---------------------- ----------------------------------------------------
  Task / Plan Manager    创建任务、拆分计划、维护状态和验收标准
  Checkpoint Store       保存任务快照、代码引用、验证结果和恢复信息
  Agent Adapter          将统一任务输入转换为 Codex/Codely 实际可执行的请求
  Workspace Manager      选择工作区、分支或 Worktree，检查环境和 Git 状态
  Handoff Coordinator    执行交接协议、确认旧 Agent 停止、转移写入权
  Policy / Ownership     控制权限、并发写入、危险操作和用户确认
  Verification Service   执行或汇总测试、CI、审查结果与验收状态
  Event / Audit Log      记录状态转换、Agent 操作、失败和恢复过程
  Shared Memory          提供经过筛选、可追溯、按需注入的工程知识

模块名称可以不同。关键是职责清晰，避免 Task 状态、Checkpoint 和 Agent
Adapter 各自保存互相矛盾的任务事实。

### 11.3 统一数据对象

V2 应设计统一的逻辑数据模型，并根据 DSH 现有存储方式决定具体 Schema。

#### Task

-   `task_id`
-   `title`
-   `goal`
-   `scope`
-   `acceptance_criteria`
-   `status`
-   `plan_version`
-   `current_checkpoint_id`
-   `workspace_id`
-   `branch`
-   `created_at` / `updated_at`

#### Session

-   `session_id`
-   `task_id`
-   `agent_id`
-   `started_at` / `ended_at`
-   `status`
-   `input_checkpoint_id`
-   `output_checkpoint_id`

Session 记录某个 Agent 一次执行活动；它不是跨 Agent 共享的完整对话转储。

#### Checkpoint

-   `checkpoint_id`
-   `task_id`
-   `schema_version`
-   `created_at`
-   `created_by`
-   `source_agent`
-   `git_commit`
-   `branch`
-   `workspace_state`
-   `completed_items`
-   `remaining_items`
-   `verification_evidence`
-   `known_issues`
-   `next_actions`
-   `required_decisions`
-   `parent_checkpoint_id`

#### Agent Adapter

统一接收： - Task 与当前计划的快照； - 当前 Checkpoint； -
仓库、分支和工作区引用； - 允许执行的操作与权限； -
需要返回的结构化结果。

统一返回： - 执行状态； - 实际修改文件； - Commit / Diff 引用； -
测试和验证证据； - 未完成项与阻塞原因； - 建议的下一步； -
是否需要用户决策。

适配器不得假设不同 Agent
的会话命令、工具能力、文件约定或退出码完全相同；能力差异应显式声明。

### 11.4 写入权与并发控制

V2 需要把 V0 的"一个任务、一个写入者"变成可执行的规则：

-   同一 Task/同一 Workspace 同时最多一个有效写入者。
-   获得写入权前检查当前 Owner 和 Workspace 状态。
-   Owner 至少记录
    `agent_id`、`session_id`、获得时间、租约过期时间和状态。
-   如果使用租约/Lease，必须处理续租、过期、进程崩溃和网络断连。
-   不能仅因为心跳丢失就立即让第二个 Agent
    修改同一工作区；先确认旧执行端已停止，或隔离旧工作区。
-   同一 Task 的并行尝试应在独立 Worktree/分支中运行，合并前进行验证。
-   状态更新应具备并发冲突检测，防止旧 Session 的迟到结果覆盖新
    Checkpoint。

### 11.5 交接事务

建议的逻辑流程：

1.  用户或 Planner 请求将 Task 从 Agent A 转交给 Agent B。
2.  DSH 暂停为 Agent A 分配新的写入动作，并请求其结束当前安全检查点。
3.  Agent A 返回变更列表、测试证据、未完成项和建议下一步。
4.  DSH 检查 Git 状态、Checkpoint Schema、任务状态和交接策略。
5.  如果验证失败，交接保持未完成，说明具体原因；不得谎报成功。
6.  按策略保存 Checkpoint，并确认代码 Commit/远程同步条件。
7.  确认 Agent A 已停止写入并释放 Owner。
8.  为 Agent B 生成统一的任务输入，包含 Task、Plan、Checkpoint、相关 ADR
    和按需 Memory。
9.  Agent B 校验工作区并确认接手。
10. DSH 原子更新 Owner、Session 和 Task 状态。
11. 执行结束后保存新 Checkpoint，进入下一次交接或 Review。

这是一项有明确失败路径的流程。任何步骤失败时都应保留原状态、报告原因，并允许安全恢复；不能把"已发出请求"当作"已完成交接"。

### 11.6 异常退出与恢复

当 Agent 崩溃、超时、电脑离线或未能正常生成 Checkpoint 时：

1.  将 Session 标记为异常/失联，而不是直接将 Task 标记为完成。
2.  读取最近有效 Checkpoint。
3.  检查 Git HEAD、分支、Diff、未跟踪文件、远程同步状态和 Worktree。
4.  若发现 Checkpoint
    之后有未提交变更，保留现场并进入恢复检查，不得自动丢弃。
5.  从 Git 历史和实际代码中重建已完成项；无法证明的事项标记为待验证。
6.  若工作区可能仍被旧 Agent
    写入，隔离工作区或确认进程停止后再授予新写入权。
7.  创建恢复 Checkpoint，注明恢复依据、缺失信息和未验证内容。
8.  只有检查通过后，才将 Task 转回 `IN_PROGRESS` 并启动新 Agent。

### 11.7 事件与审计

至少记录这些事件（可映射到 DSH 现有事件系统）：

-   `TaskCreated`
-   `PlanUpdated`
-   `SessionStarted`
-   `CheckpointCreated`
-   `HandoffRequested`
-   `HandoffBlocked`
-   `OwnershipReleased`
-   `OwnershipAcquired`
-   `HandoffCompleted`
-   `VerificationCompleted`
-   `TaskBlocked`
-   `TaskCompleted`
-   `RecoveryStarted`
-   `RecoveryCompleted`

事件应包含 Task、Session、Agent、时间、结果、关联 Commit/Checkpoint
和错误摘要。日志不应保存 API Key、Token 或完整的敏感环境变量。

### 11.8 DSH 的渐进迁移策略

1.  DSH 先读取 V0 的 Markdown Task 和 Checkpoint。
2.  为 Markdown Schema 建立版本号和兼容读取逻辑。
3.  在不改变用户工作流的情况下，将其导入 DSH 的 Task/Checkpoint Store。
4.  DSH 先提供只读状态展示和校验。
5.  再让 DSH 发起人工确认的交接。
6.  验证可靠后，再逐步自动化 Owner 转移、恢复和验证。
7.  最后才考虑更深度的 Agent 启动/停止集成；具体执行能力由现有 DSH
    架构和已确认 ADR 决定。

不要在一次迁移中同时更改 Task 状态模型、存储、Agent 接口和 Git
工作区策略。

### 11.9 V2 验收标准

-   [ ] DSH 是 Task/Checkpoint/Owner 状态的单一权威入口。
-   [ ] Codex 与 Codely 通过适配器接入，不依赖跨产品原生会话恢复。
-   [ ] 同一工作区不会被两个 Agent 同时授予写入权。
-   [ ] 交接具备成功、失败、取消、超时和异常退出路径。
-   [ ] 旧 Session 的迟到结果不能覆盖更新的状态。
-   [ ] Checkpoint 与 Git Commit/Workspace 状态关联可追溯。
-   [ ] 恢复过程不会丢弃未提交用户修改。
-   [ ] 权限、危险操作和用户确认符合现有 DSH Policy。
-   [ ] V0 Markdown 可按版本导入，旧数据不会无提示丢失。
-   [ ] 有状态机、并发、异常恢复和集成测试。
-   [ ] 现有 DSH 架构决策没有被绕开或重复实现。

## 12. 端到端测试清单

### 12.1 基础接力

-   [ ] Codex 开始 Task，完成部分工作并写入 Checkpoint。
-   [ ] Codely 接手后能识别已完成项并只执行下一步。
-   [ ] Codely 交接回 Codex 后，状态和代码版本仍一致。
-   [ ] 交接文档更新但产品代码未变时，不会错误声称产品代码重新通过测试。
-   [ ] Agent 只完成部分计划时，Task 不会被标记为 `DONE`。

### 12.2 Git 与工作区安全

-   [ ] 工作区干净时正常交接。
-   [ ] 存在与任务相关的未提交 Diff 时，交接明确记录。
-   [ ] 存在与任务无关的未提交修改时，不会误提交。
-   [ ] 存在未跟踪文件时，交接检查能提示。

### 12.3 决策与上下文

## 13. 风险与回滚策略

  ----------------------------------------------------------------------------
  风险                                缓解方式
  ----------------------------------- ----------------------------------------
  两个 Agent 同时修改同一工作区       V0 手动停止旧 Agent；V2 通过 Owner/Lease
                                      和 Workspace 隔离

  Checkpoint 与代码不一致             接手时核对 Git
                                      和测试证据；以可验证事实为准

  共享 Memory 膨胀                    只保留稳定知识；Task
                                      细节放在各自任务目录

  Agent 擅自修改架构                  ADR 变更必须走明确审查和批准流程

  自动脚本误改文件                    V1 默认只读校验；写操作限定范围并展示
                                      Diff

  跨设备代码没有同步                  显式记录 Push 状态；新设备必须验证
                                      Commit

  Agent 异常退出                      保留现场、从 Git 与最近有效 Checkpoint
                                      恢复

  V2 过度设计                         先验证 V0/V1
                                      的真实使用模式，再按需求增量实现

  与现有 DSH 设计冲突                 先检查现有
                                      ADR/模块，复用已有能力，不新建平行体系
  ----------------------------------------------------------------------------

### 回滚原则

-   V0：保留新增文档和任务记录即可；如果入口文件修改不适用，只回滚本次明确添加的引用，不覆盖用户原内容。
-   V1：脚本和 Skills 可以单独停用；Task Markdown 仍然可手动使用。
-   V2：先停用自动调度/交接入口，再恢复人工工作流；保留 Task、Checkpoint
    和审计记录，不直接删除状态数据。
-   任一阶段失败，都必须让用户仍可用 Git 和 Markdown 接力工作。

## 附录 A：最小可行工作流摘要

如果 Agent 只记得一件事，应记住以下顺序：

**接手前：读取规则 → 读取 Task/Plan/Checkpoint → 检查 Git → 核对事实 →
确认唯一写入权 → 继续下一项。**

**交接前：停止修改 → 检查 Diff/未跟踪文件 → 验证并记录结果 → 更新
Plan/Checkpoint → 安全保存代码与文档 → 按授权同步 → 释放写入权。**

**异常恢复：不清理现场 → 核对 Git 与最近有效 Checkpoint →
未验证项重新验证 → 明确风险 → 确认旧写入者已停止 → 恢复任务。**

## 附录 B：术语

-   **Task**：具有目标、范围、计划和验收条件的工作单元。
-   **Session**：某个 Agent 针对 Task 的一次执行过程。
-   **Checkpoint**：足以让另一 Agent 安全接手的结构化状态快照。
-   **Handoff**：停止旧写入者、保存状态、验证代码事实并把任务交给新
    Agent 的完整流程。
-   **Workspace**：Agent 实际读写的工作目录、分支或 Worktree。
-   **Owner / Lease**：当前被允许写入某 Task/Workspace
    的执行者及其有效期。
-   **ADR**：经过明确确认的架构决策记录。
-   **Shared
    Memory**：经过筛选、长期有复用价值的工程知识；不等于聊天历史。
