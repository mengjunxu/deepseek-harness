# P1-07 原生会话续接能力

在 macOS 本机用两个连续启动的产品进程、同一临时工作目录和回环模型完成验证。第二轮只提交通用续接提示。验证依据包括进程退出、原生恢复响应和本地模型端点实际收到的输入；原始会话、命令行凭据和请求载荷未写入验收工件。[结果与文件摘要](evidence/local.json) · [复测脚本](evidence/probe.mjs)。

**Codex 0.153.4** 使用包内固定的 app-server。持久线程恢复后返回同一线程与首轮 turn ID。第二轮模型输入含首轮用户消息与助手答复，同样的提示在新线程中不含这两项。当前适配器创建的临时线程和从未创建的 ID 均收到产品错误 -32600。

**Codely 1.0.0-nightly.53** 的两个标准 ACP 方法 `session/load`、`session/resume` 均返回 -32601。其专用 `session/new` 参数 `_meta.codely.resumeSessionId` 能在重启后找回已保存的会话。第二轮发送前，匹配 ID 的 `replace_history` 通知含首轮问答，随后实际模型输入也含这两项。以未知 ID 调用同一扩展时，产品回显所给 ID、发送空历史且可继续处理提示。调用方如要保证续接，需把恢复历史与前序 Run 保存的位置核对。同一版本的 CLI 检查点标签与跨设备恢复均不在本步实测范围。

**工作台** 当前仅允许新建原生会话。已在两种执行器的 Web/SDK 测试中复核，恢复备份后显式选择原执行器、以及省略执行器的续接请求都被拒绝。原 Run、待人工验收交付和模型请求数未变。[命令与检查结果](log.md)。

本步变更为探针、既有 Web 回归夹具、主实施计划、工程进度与共享记忆索引。工作树还有前序任务的本地改动。未提交或推送；本地分支与远端跟踪引用提交差为零。与上步相同，doc-sync 37/42，五项既有问题为文档示例类型、Markdown 链接、双语配对、旧文档换行及旧记录提交引用。

下一项是接入工作台的原生续接。可先从 Codex 的显式持久 Run 入手，在启动时记录原生线程与已完成轮次，将其绑定至执行器、项目和工作目录，在再次派发前核对历史位置。现有临时 Run 没有可用于恢复的持久线程。Codely 接入还需要解决未知 ID 可以返回成功的情况。跨设备验收、G2 参考机与草稿 PR 仍按用户安排待验。本步没有更改产品架构或共享工作流。
